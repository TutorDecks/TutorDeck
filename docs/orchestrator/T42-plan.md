# T42 plan: HitPay "Pay now" for centres (optional add-on)

Branch `claude/t42-plan`. Plan only: no product code, no SQL, nothing deployed, LIVE and DEV untouched, no secret used. Written 2026-11-26. Read: CLAUDE.md, `assets/js/org-settings.js` (section "How parents pay"), `docs/orchestrator/T4-plan.md` and `T34-plan.md` (their branches), branch `claude/t4-s3-payments` (`db/migration_centre_payments.sql`, `assets/js/pay.js`), `api/stripe-webhook.js`, `api/_billing-lib.js`. HitPay's own docs were fetched on 2026-11-26 (docs.hitpayapp.com: online payments, webhooks, sandbox, payment methods, refund and payment-status API pages, hitpayapp.com/paymentapis). Anything I did not read says **not verified**. Money, tax and PDPA points are for the owner's accountant or lawyer; this is not advice.

## Summary
- **What it is:** a centre that has its **own** HitPay account switches on payment mode `hitpay`. The share-link page then shows **Pay now**; the parent pays on HitPay's page (PayNow by default); HitPay tells us by webhook; we record an ordinary payment (method `hitpay`) through the **same internal function as manual payments**. TutorDeck never touches the money: it goes to the centre's HitPay balance and out to the centre's bank.
- **Mode is `soon` today** (`org-settings.js` l.109, l.115-116). Nothing exists to build on except the S3 payment tables and share page (branch `claude/t4-s3-payments`, not on `dev` yet).
- **Safety design:** the centre's key and salt are stored **encrypted, server-side only**, never sent back to a browser; the webhook **verifies HitPay's signature, then confirms the payment by asking HitPay directly** with the centre's key; every event is idempotent; anything unexpected (wrong amount, late, duplicate, refund) goes to a **review queue** and a person decides. No automatic wrong allocation, no automatic reversal.
- **Fees:** absorbed by the centre by default. Pass-on cannot edit an issued invoice, so my recommendation is a **separate fee receipt created at pay time** (section 2).
- **Payouts:** a HitPay payout that lands in the bank must **never become a payment**. T34's statement matching gets one extra first rule (section 3).
- **Nine small steps** (H0-H8, section 5), about **17 worker-days** (plus or minus 30%), each shippable and clickable on DEV against the **HitPay sandbox** (it exists). Needs T4 S1-S3 first; H7 also T34 M3.
- **Recommendation: build after the committed first-customer scope**, except a half-day read-only sandbox check (H0). Six decisions for the owner in section 7.

## 0. What HitPay's documentation says (verified 2026-11-26, from docs.hitpayapp.com)

| Methods | Enums `paynow_online` (PayNow) and `card`. If `payment_methods[]` is omitted, **every method enabled on the account** is shown, so we always send an explicit list. Sandbox supports PayNow, cards, GrabPay, ShopeePay, Atome. |
| Redirect | After paying, HitPay sends the browser to `redirect_url` with `reference` (the request id) and `status`. HitPay says this URL "can be triggered by anyone" and must **not** mark an order paid. |
| Webhooks | Registered **by the account holder** in the HitPay dashboard (Developers > Webhook Endpoints; URL must be HTTPS and public). The docs call both "your salt"; **which one signs `payment_request.completed` on a dashboard webhook is not unambiguous: to settle in H0.** Salts differ between sandbox and production. |

## 1. The flow
**Connect (owner only).** Settings > How parents pay > HitPay card: the centre owner picks **Test (sandbox)** or **Live**, pastes the **API key** and the **webhook salt**, sees the URL to paste into HitPay (Developers > Webhook Endpoints: `https://<host>/api/hitpay-webhook?c=<connection id>`, events `payment_request.completed`, `payment_request.failed`, `charge.updated`, `payout.created`). The browser sends the two values once over HTTPS to `api/hitpay-connect` with the user's session; the function checks "owner of this org", encrypts, stores, and answers only `connected, key ending ····1234`. **Never returned again**; replacing = typing new ones. "Check connection" = one authenticated read call (which one: H0; fallback: the invalid-key error) plus, for the salt, the **first correctly signed webhook** (shown as "first webhook received ✓"; it cannot be tested earlier). `hitpay` cannot be saved in `payments.modes` until the check passed (`org_validate_settings`), and PayNow and/or cards must be on.

**Where secrets live.** Table `org_gateway_secrets` (no browser policy at all, `revoke all` from `anon, authenticated`, `service_role` only). Recommended: **application-layer AES-256-GCM** in the server function with a master key held only in Vercel env vars (a **different** one for Production and Preview, like the Supabase keys: previews use DEV), a `key_version` column for rotation. Then the database, its dumps and the nightly backups hold ciphertext only. **Alternative: Supabase Vault** (a Postgres extension in Supabase's documentation, from memory); whether DEV and LIVE have it enabled and what the plan allows: **not verified** (I did not query either project). Both are fine; app-layer needs no plan feature.

**Pay now.** `pay.html` already shows the invoice from its secret link. If `hitpay` is on, connected and balance > 0 it also shows **Pay S$X now** (and "pay another amount" only if `payments.partial_payments` is on; never above the balance). Click -> `api/hitpay-pay` (token only, rate limited) -> database function checks the invoice is issued and unpaid, picks the amount, writes a `hitpay_requests` row -> server calls HitPay with: amount from cents by integer formatting (never `parseFloat`), `currency=SGD`, `reference_number` = the invoice number, `purpose` = "Invoice INV-12", **no student or parent names**, explicit `payment_methods[]` from the centre's switches (**PayNow on, cards off by default**; when cards are on the page shows both fees in dollars: from the published rates a S$400 invoice costs about S$2.90 by PayNow and S$11.70 by card, computed with half-up cents, rates editable per centre), `redirect_url` = `/pay?t=<token>&hp=return`. The page shows "confirming your payment" and reads **our database**, never the redirect's `status`.

**Webhook** (`api/hitpay-webhook`, pure logic in `api/_hitpay-core.js`, same split as `_billing-core.js`):
1. Read the **raw bytes** (size cap 64 KB); unknown connection id or a wrong signature -> the same generic answer, nothing stored except a counter the owner can see ("3 unsigned requests rejected today"). HMAC-SHA256 over the raw body with the connection's salt (current and, during a rotation, previous), hex, `timingSafeEqual`.
2. **Confirm by fetch** (recommended): call `GET payment-requests/{id}` with the centre's key and require status completed and the same amount and currency. A leaked salt alone then cannot forge a payment. If the fetch fails: answer 500 so HitPay retries (retry behaviour not verified), and a later "reconcile open requests" button re-asks.
3. Parse amounts from text to cents (reject more than 2 decimals). Insert into `hitpay_events` with a unique key `(org, hitpay payment id, kind, cumulative refunded cents)`: a repeat inserts nothing and answers 200 ("duplicate"). The Stripe webhook's "event id first, forget it if handling fails" pattern is the model.
4. **Decide** (SQL, one transaction): **auto-record only if all hold**: request is ours and still `created`; amount equals the requested amount and currency SGD; invoice still `issued`; requested amount is not more than the invoice's balance now; setting `payments.hitpay.auto_record = exact`. Then call the internal payment function (below). Anything else -> state `needs_review` with a plain reason.
5. Store no buyer name, email, phone or card detail: ids, cents, status, method type, HitPay's `fees`, a payload hash. Never log bodies or headers.

**Recording.** S3's `centre_record_payment` is gated by `auth.uid()` and permission, so a webhook cannot call it. Plan: S3 (or T34 M3, whichever builds first; both need it) extracts the body into `centre_payment_core(...)` with no auth check; the staff function and a new `hp_ingest_event` (service role only) both call it, so allocation order, partial payments, overpayments, family credit and reversal behave **identically**. Needed changes: add `hitpay` to the `method` check lists of `centre_payments` and refunds, and a unique index on `(org, reference)` where method is `hitpay`. The **HitPay payment id is the payment's `reference`** (already redacted in the audit copy by `centre_money_audit`); the audit summary line carries amount and method only. Actor: `recorded_by` is null and the audit row says `via hitpay webhook`.

**Cases**
| Case | Handling |
|---|---|
| Part payment | A request has a fixed amount, so each part is its own request and payment, allocated normally. Parts exist only if `payments.partial_payments` is on (otherwise "Pay in full" only). |
| Duplicate delivery | Unique key: 200, nothing new. |
| Same invoice paid twice (two tabs, two QR codes) | Second one exceeds the balance -> `needs_review` "paid twice: S$X more than owed". Choices: keep as family credit (per `payments.overpayments`), or refund in HitPay then confirm the notice. |
| Late webhook (invoice since paid by hand, voided, credit-noted) | Money did arrive, so it is **never dropped**: `needs_review` with the reason; default suggestion family credit. |
| Failed or expired | `payment_request.failed` -> request `failed`, invoice untouched, page offers Try again. Our own `expires_at` (24 h) marks requests `expired`; a payment on an expired request still arrives (QR cannot be cancelled) and takes the **late** path. A new Pay now supersedes older open requests in our table only. |
| Amount, currency or unknown request mismatch | `needs_review`, no payment. A person with `record_payments` chooses: record to INV-x, household credit, or ignore (reason typed). |
| `auto_record = never` (centre's choice) | Every HitPay payment waits in the queue for one click. |

**Refunds made in HitPay.** `charge.updated` with a higher `refunded_amount` creates a **refund notice** (to confirm), never a change. A person with `record_payments` picks what it is: (a) a mistaken payment -> `centre_reverse_payment` (S3's reversal is whole-payment only: one reversal per payment is enforced, so a **partial** refund = reverse and re-record the kept part in one audited function); (b) refund of a **deposit** -> attach to S5's refund record as "paid, method hitpay, reference = refund id" (the deposit ledger gets `refunded`; the payment is **not** reversed); (c) refund of **family credit** -> S3's `centre_refund_family_credit` with method `hitpay`. TutorDeck does not start refunds in v1 (HitPay's refund API exists; a "Refund" button would put money-moving power behind the stored key: decision 6).

## 2. Gateway fees (`payments.gateway_fees`)
- **`absorb` (default):** invoice and payment unchanged. HitPay's reported `fees` is kept on the event for reconciliation only (it is a cost of the centre, not an invoice item).
- **`pass_on`:** an **issued invoice is never edited**, and the fee depends on how the parent pays (PayNow vs card) and how much, which is unknown at issue. Three ways, recommendation first:
  1. **Fee receipt at pay time (recommended).** When the parent taps Pay now, the server computes the fee for the chosen method and amount and shows "Invoice S$400.00 + online payment fee S$2.92 = S$402.92" **before** they pay. HitPay is asked for the total; the invoice is credited with S$400.00 and the S$2.92 becomes a small **immutable fee receipt** (own number series via `org_counters`, linked to the payment, shown on the share page and in "Payments"). Nobody who pays by bank transfer is charged. The fee is **grossed up** so the centre nets the fee back: `f = round_half_up((rate x X + fixed) / (1 - rate))`, in integer cents with `money.js` (checked: for X = S$400.00, PayNow 0.65% + S$0.30 gives S$2.92 and HitPay's published fee on S$402.92 is also S$2.92). Rates are centre settings pre-filled with the published ones, so a negotiated rate works; actual `fees` can differ by a cent or two and the report shows the difference.
  2. **A line on the invoice at issue**, computed for one centre-chosen method, only possible when the invoice run knows `pass_on` is on. Simple and immutable but families who pay by bank transfer are charged too, and a fix needs a credit note. Not recommended.
  3. **Do not build pass-on in v1** (`soon`), absorb only. Fastest, always honest.
- **GST:** if the centre is GST-registered the fee line is probably part of what the centre supplies, so GST once per document at the centre's rate, half up, by the same SQL function; **accountant to confirm** (disbursement vs supply, document wording). Unregistered centres: none. A surcharge needs to be in the terms parents accepted (lawyer).
- A deposit invoice may carry a fee too; a **setting `payments.hitpay.deposits_online`** (yes/no) lets a centre keep deposits off Pay now.

## 3. Reconciliation and statement matching
- **`hitpay_payouts`** (from `payout.created`): id, net cents, date, **last 4 of the account only** (the payload carries the full number; never stored), state `in_transit / in_bank`.
- **Report** (Payments > HitPay): per period, recorded HitPay payments (sum) minus HitPay fees minus refunds = **expected payout**; payouts received; **difference** split into "in transit" (recorded after the last payout) and "unexplained" (red). Which charges a payout contains is **not verified**, so v1 reconciles by totals and dates, not line by line (H0 checks whether a transactions or balance API makes it exact).
- **No double count (T34).** A payout is a lump sum in the bank that matches **no invoice**; rules C and D (amount only, household total) could wrongly pair it with an open invoice. Add **rule 0, before A-D**: a credit line equal to a recorded payout's net amount within the centre's window (default payout date to +5 days; setting) is proposed or auto-linked as kind `gateway_payout`, which **only marks the payout "in bank" and never calls the payment function**. A credit whose text looks like HitPay (bank wording **not verified**) with no payout record is held for review with the single action "Mark as HitPay payout"; rules A-D skip it. Test: a payout equal to an open invoice's balance creates no payment; a HitPay-paid invoice is not "open", so no line can pay it twice.
- A parent who pays the centre's PayNow directly (not via HitPay) is a normal manual or statement payment; HitPay's own PayNow never touches the centre's bank until payout.

## 4. Deposits and credit notes
- A deposit invoice (T4 S4) is an ordinary issued invoice, so HitPay pays it through the same core function and S4's ledger shows `received`; no deposit-specific webhook code. Refund of a deposit: a person links a HitPay refund to S5's refund record (section 1, (b)).
- A credit note after a HitPay payment raises family credit exactly as for manual payments; paying that credit back through HitPay is recorded with method `hitpay` (c). Credit notes never call HitPay.

## 5. Data model, functions, tests, build order
**Tables** (all with `org_id`, same-org composite keys, on delete cascade so account deletion covers them, **no insert/update/delete policy**, read policy by permission, solo orgs and non-members get `NOT_FOUND`): `org_gateways` (provider, mode sandbox/live, status, key last 4, connection id, last check, last webhook; readable by owner and `record_payments`), `org_gateway_secrets` (ciphertext, nonce, key version; **no policy, no grant to any browser role, no row-audit trigger** because the generic audit copies whole rows: functions write a summary audit entry instead), `hitpay_requests`, `hitpay_events` (idempotency key, decision, reason, linked payment), `hitpay_payouts`, `hitpay_fee_receipts` (S6). **Functions (SECURITY DEFINER, search_path pinned, audited):** browser-callable `hp_connection_status`, `hp_review_queue`, `hp_resolve_event`, `hp_confirm_refund_notice`, `hp_recon_report`; **service role only** `hp_save_secret`, `hp_load_secret` (returns ciphertext; decryption happens in the server function), `hp_prepare_request`, `hp_attach_request`, `hp_ingest_event`. Tutors: no access to anything here; `tutor_my_lessons` untouched. New settings (validated in `org_validate_settings`, enums checked by `tests/org-settings.test.js`, unbuilt values `soon`): `payments.hitpay.auto_record` (`exact` / `never`), `payments.hitpay.fee_rates`, `payments.hitpay.deposits_online`, `payments.hitpay.payout_window_days`; existing `hitpay.paynow`, `hitpay.cards`, `gateway_fees` lose their `soon` flag step by step.

**Tests (no real network, ever).** (1) `tests/fixtures/fake-hitpay.js`: a local server that implements create, get-status and refund, hands out ids, and **signs** webhooks with a given salt; switches for duplicate, delayed, out-of-order, wrong signature, wrong amount or currency, unknown request, partial refund, 500 on fetch. HitPay's base URL comes only from two constants by mode, **never an environment override** (no way to point a production function at another host); tests inject `fetch` into `_hitpay-core.js`. (2) **Signature vectors:** fixed (salt, raw body, expected hex) triples, each computed with two independent implementations (Node and Python agreed on a sample I ran today); cases: correct, one byte changed, re-serialised JSON (spaces differ), wrong salt, empty or missing header, upper-case hex, wrong length. (3) **Unit** (`tests/hitpay-core.test.js`): text-to-cents (`"100.00"`, `913.84`, `"0.1"`, reject `"1.234"`), fee vectors shared with SQL, decision table. (4) **SQL** (`tests/sql/`, throwaway Postgres): one test per case in section 1 and per value of `auto_record` and `gateway_fees`, cross-org, solo, tutor, parent and missing-permission refusals, **no ciphertext or key in any audit row, error text or function result**, no personal data in events, duplicate adds zero rows, refund notice changes nothing until confirmed, payout never makes a payment. (5) An integration script wires fake server + Postgres + the handlers.

## 6. PDPA and security risks
| Risk | Plan |
|---|---|
| **Webhook spoofing / replay** | Signature on raw bytes, constant-time compare, confirm-by-fetch, idempotency key, size cap, generic errors, rate limit per connection, event types allow-listed, owner sees "rejected requests" count. No timestamp is signed (replays possible), so idempotency is the defence. |
| **Key or salt leaks** | Encrypted at rest, master key only in Vercel (separate for Preview/Production), never returned, never logged (`Authorization`/key headers stripped from error text), no audit copy, backups hold ciphertext only. The pasted key transits the owner's browser once (password input, no autofill). A leaked API key could create requests or refund, so the key is entered by the **owner only**, and the centre should use a key with the least rights HitPay offers (not verified whether keys can be limited). |
| **Rotation / disconnect** | "Replace" stores a new version; old salt accepted 24 h; a new connection id is issued and the old URL gets 410 after 7 days. Disconnect deletes the secret rows. Account deletion cascades. Tell the centre to revoke the key in HitPay (we cannot). |
| **Personal data** | HitPay's payloads hold buyer name, email, phone, card brand, last 4 and (payouts) a full bank number. We keep none of it (ids, cents, status, method type, fee, hash, last 4 of the account). We send HitPay only an amount, the invoice number and a purpose line; no names. Parents' data goes to HitPay under the **centre's own** HitPay agreement; the privacy notice and whether TutorDeck is the centre's data intermediary here: lawyer. |
| **Logs** | No bodies or headers; ids only; the connection id in a URL is a routing id, not a secret, so it may show in Vercel logs. |
| **Wrong host** | Mode (sandbox/live) is explicit per centre; the DEV project can only hold sandbox keys (a live key typed into DEV is refused by a prefix/mode check **not verified for HitPay key formats**, so H0 checks); production webhook URL on the production domain only. |

## 7. Risks and decisions for the owner (recommendation first)
1. **Before or after the first-customer scope?** **Recommend after** (S0-S5, S7-S8 and T34 first): HitPay is optional and not in the first price, adds a public endpoint plus stored third-party keys, and depends on the centre's HitPay onboarding (time not verified). Do **H0** now (half a day, read-only) so the answers are ready. Alternative: after S3 only, if a second centre asks for card payments.
2. **Fee pass-on.** **Recommend the pay-time fee receipt** (section 2, way 1), built last (H6) with `pass_on` marked `soon` until then; accountant to confirm GST and wording. Alternative: absorb only in v1.
3. **Key storage.** **Recommend application-layer AES-GCM** (works on any plan). Alternative: Supabase Vault once a read of both projects shows it is enabled (not verified).
4. **Auto-record default.** **Recommend `exact`** (record only when everything matches; otherwise queue), with `never` available. Alternative: always queue in the first release.
5. **Confirm-by-fetch.** **Recommend yes**: slightly slower, much safer if a salt leaks. Depends on H0 confirming the status endpoint's shape. Alternative: signature only.
6. **Refunds from inside TutorDeck.** **Recommend not in v1**: people refund in the HitPay dashboard and confirm the notice here. Alternative: a "Refund" button (HitPay's refund API exists) behind owner-only approval, later.
Also: PDPA wording, surcharge terms and accountant questions above are for your lawyer and accountant; Vercel Pro and a HitPay Live account are go-live prerequisites (add to the CLAUDE.md go-live list when this ships).
