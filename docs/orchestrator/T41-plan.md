# T41 plan: WhatsApp delivery for centres (manual by default, automatic with the centre's own account)

Branch `claude/t41-plan`. Plan only: no product code, no SQL, nothing deployed, DEV and LIVE untouched, no secrets used. Written 2026-11-26. Read: CLAUDE.md, `assets/js/org-settings.js`, the solo WhatsApp code in `assets/js/ledger.js` (templates, `waNumber`, `fillTemplate`), `api/_gcal-lib.js` and `api/stripe-webhook.js` (how server code seals data and checks signatures), `docs/orchestrator/T4-plan.md` and `T7-plan.md` (branches `claude/t4-plan`, `claude/t7-plan`), the Product Guide. Meta and Supabase pages were fetched and read on 2026-11-26 (list at the end). Anything not read is marked **not verified**. Legal points are for the owner's lawyer; this is not advice.

## Summary
- **Two modes, one setting.** `manual` (default): TutorDeck writes the message and opens WhatsApp (`wa.me`); a person presses send; TutorDeck records only "opened by X", never "delivered". `api` (optional add-on, not in the first customer's price): the centre pastes its **own** WhatsApp Business credentials; TutorDeck sends approved **template** messages from a server queue. `off` is also a value. Email is a separate switch (T7).
- **Build manual first and keep it small:** per-centre templates, a send log, and a "next family" queue so 400 families can be worked through in one sitting (realistically about an hour at 10 s each: an estimate to time on DEV). It also is the **fallback** for everything the automatic mode cannot send.
- **Correction to the brief:** Meta now bills **per delivered message**, by category and country, not per conversation (pricing page, effective 1 Jul 2025). The centre pays Meta directly; TutorDeck never holds that money.
- **What Meta requires (verified):** an approved template for any message sent outside the 24-hour window that opens when a parent writes to the centre (all our messages are such); opt-in from each recipient; a long-lived system-user token; a new account may message only **250 unique numbers per 24 h** until the business is verified (then 2,000, then it scales). A 400-family run therefore needs a verified business.
- **Secrets:** tokens are sealed on the server (same AES-256-GCM method `api/_gcal-lib.js` already uses, key only in Vercel env), stored in a table nobody can read from the browser, never returned after saving, used only by `api/` functions. Supabase Vault is real but its plan availability is **not verified**; recommend the repo's own method.
- **Provider-agnostic?** A thin adapter (4 functions) with two implementations, `meta` and `fake`, because the fake is needed for tests anyway. No second real provider now.
- **Build order:** W0-W4 manual (about 7 days), W5-W9 automatic with a fake provider on DEV (about 15 days), real Meta test last. Total about 22 working days, one worker, estimate.
- **Recommendation: build the manual part right after T4 step S3; the automatic part after the committed first-customer scope.** Six decisions in section 7.

## 1. Manual mode (default)
**Where the buttons are** (staff with the existing `issue_invoices` / `record_payments` permission; tutors never see parent contacts unless `tutors_see_parent_contact`):
| Message | Button | Fills from |
|---|---|---|
| Invoice | on each issued invoice: "Send on WhatsApp" | household guardian, invoice number, total, due date, **share link** (T4 `invoicing.delivery.share_link`, so this needs it on) |
| Reminder | on each overdue / due-soon invoice, and on the Reminders list | same, plus the schedule offset |
| Per family | on the household page: a free-text message | name only |
| Remark | on a lesson remark, staff only | **link to the portal remark**, never the remark text (child data) |

**Templates.** One editable text per message kind per centre (invoice, reminder before due, due today, overdue, remark notice), with the placeholders the solo app uses (`{name}` `{student}` `{business}` `{amount}` `{invoice}` `{date}` `{link}`), a live preview and "reset to default". The fill logic moves into a shared tested file (today it is private to `ledger.js`, a hotspot: the move needs the owner's yes; solo behaviour must not change). Stored in a new `org_message_templates` table, edited by staff with `manage_settings`, versioned (append-only), so the log can say which wording was used.
**Never put bank account numbers in a manual or automatic template**: link to the invoice page, which shows the PayNow QR (Meta's policy also says not to share financial account numbers: **verified** wording, how it applies to a centre's own PayNow ID is **not verified**).

**What is logged.** One append-only `message_log` row per press: kind, subject (invoice / household / remark), guardian, template version, `channel = whatsapp_manual`, `event = opened` and who/when. Staff may then tap "Sent" or "Skip". The UI says **"Opened WhatsApp by Jane, 14:02"**, never "delivered" or "read": WhatsApp gives no receipt for a message typed in someone's own chat. No message text is stored.

**Bulk: "Next family" queue.** One card at a time: family, what is owed, the message preview, and big buttons **Open WhatsApp** / **Skip** / **No number** / **Do not contact**. After "Open", the card waits for "Sent" (one tap, or Enter) and the next family loads; the list is resumable (a family already opened today is hidden), filtered (only ready invoices, only with a valid number), and shows "37 of 400". Families without a valid number go to a "Fix these numbers" list. Honest limit: staff still press send 400 times; the real saving is automatic mode.

**Numbers and consent.** Stored as +65 E.164 with one normaliser shared by browser and server (same rules as today's `waNumber`: 8 digits get 65, leading zeros stripped; reject under 8 or over 15 digits; warn on a number starting with 6, likely a landline: common knowledge, **not verified**). Meta says to always send with the plus and country code, otherwise the business's own country code is prepended and the message can go to the wrong person (**verified**). Consent: each guardian gets `whatsapp_consent` (unknown / yes / no), date and source (enrolment form, in person, other) and a `do_not_contact` flag. Manual mode never blocks on "unknown" (a person is choosing), but refuses on "no" and shows a warning on "unknown"; automatic mode sends only on "yes" (section 2).

## 2. Automatic mode with the centre's own credentials
**What Meta requires (all verified unless stated):**
- A **Meta business portfolio**, a **WhatsApp Business account**, a **business phone number**, and an app in Meta's developer dashboard. A **system user** creates a long-lived token with three permissions: `business_management`, `whatsapp_business_management`, `whatsapp_business_messaging`; the person chooses an expiry when generating it, so tokens can expire and the screen must show "reconnect needed".
- **Templates.** Outside a customer service window (24 hours, reset each time the parent writes) only approved template messages may be sent. A template needs a name (lowercase letters, digits, underscore), a language, a category (utility / marketing / authentication), body text with named or positional parameters **plus an example for each**, and is reviewed automatically (the page says review can take up to 24 hours). Only status `APPROVED` can be sent. Templates can be paused or disabled by poor feedback; archived after 12 months unused; at most 100 created per hour. A "utility" template that contains marketing material is automatically re-categorised as marketing (**verified**), which prices and limits it differently, so wording stays strictly transactional.
- **Cost.** Per delivered message, by category and the recipient's country code (Singapore +65 is in the rate table). Messages from parents to the centre are free; 1,000 service (free-form, in-window) messages a month per number are free. Each Messaging account has its own payment method. **The Singapore per-message rate: not verified** (read the rate card at build time; never hard-code it).
- **Opt-in and opt-out.** The centre must have each recipient's opt-in, naming the business, by any lawful method (paper and in-person count), and must honour opt-outs. Blocks and reports lower the quality rating and can throttle or remove access.
- **Limits.** Unique recipients per 24 h outside the window: 250 for a new portfolio; 2,000 after business verification (or after 2,000 delivered template messages with good quality in 30 days); further levels scale automatically. The tier is readable by API (`whatsapp_business_manager_messaging_limit`).
- **Webhooks** (delivery statuses, template status, inbound messages): a GET handshake with a verify token; each POST carries `X-Hub-Signature-256`, an HMAC-SHA256 of the raw body with the **app secret**; answer 200; Meta retries failures for up to 7 days (duplicates happen); up to 1,000 updates per POST; no history API (store what you need); order of messages is not guaranteed; a message not reported `delivered` within its 30-day time-to-live is dropped. Users may adopt **usernames**: then phone fields can be missing in webhooks and a business-scoped user ID is used (**verified**), so match statuses by **our stored message id** (`wamid`), not by phone.

**Design**
1. **Connect (owner only, Settings, "WhatsApp Business")**: fields: WhatsApp Business account ID, phone number ID, system-user token, app secret, a verify token TutorDeck generates and shows to paste into Meta. "Save" calls one server function; afterwards the screen shows only "Connected as +65 xxxx 1234, tier 250, checked 2 min ago" and **Replace / Disconnect**. Never the token, not even part of it.
2. **Storage.** `org_wa_credentials` (separate table, RLS on, **no policy for anyone**, `org_id` with `on delete cascade` so account deletion stays covered). Ciphertext sealed in `api/` with AES-256-GCM and a key id, key in Vercel env (`WA_TOKEN_KEY`, different value on Production and Preview). Why not Vault: Supabase's Vault page (read) describes an encrypted `vault.secrets` table with a per-project key kept outside the database and decrypted through a view; **whether it is enabled and allowed on this project's plan: not verified** (check with a read-only `pg_available_extensions` query in step W5). Same-method precedent in the repo, no plan dependency, and the nightly backups then hold ciphertext only. Decrypting happens only inside `api/` with the service key; a SQL test proves no role, including the owner's, can select the table or any function return the token.
3. **Connection check button**: server calls Meta for the phone number record (display number, verified name, messaging limit) and the template list; stores the result (state, tier, quality, timestamp), never the raw response.
4. **Template management.** A fixed TutorDeck set per centre, created through Meta's template API from a button ("Create the 5 templates"), each stored in `org_wa_templates` (kind, Meta name, language, category, Meta status, last webhook update). Mapping:
| TutorDeck message | Meta template name | Meta category (expected, Meta decides) |
|---|---|---|
| Invoice issued | `td_invoice_issued` | utility |
| Reminder before due (offset < 0) | `td_payment_due_soon` | utility |
| Due today (offset 0) | `td_payment_due_today` | utility |
| Overdue (offset > 0) | `td_payment_overdue` | utility, risk of re-categorisation |
| Remark ready | `td_remark_ready` | utility; link only, **soon** until the portal exists |
Parameters are fixed per kind (first name, student first name, amount, invoice number, due date, link); the centre edits wording rarely because every edit is re-reviewed. A kind with no `APPROVED` template is not sendable and its messages go to the manual list. Whether a **link** may be a body parameter or must be a URL button: **not verified**, settled in W8 against the real review.
5. **Sending queue** (`wa_outbox`, written by SQL functions; no browser write policy): states `queued → sending → accepted → delivered → read`, or `failed / skipped / cancelled / needs_manual`. One unique key `(org, kind, subject, schedule offset)` makes every action **idempotent** (running the invoice run or the daily job twice sends nothing twice). Rules checked **before** a row is sent: guardian consent = yes and not opted out; valid +65 number; template `APPROVED`; inside the centre's send hours (setting, default 09:00 to 20:00 Singapore); under the **daily cap** (setting, never above the tier read in the last connection check); invoice still unpaid at send time (a reminder is re-checked, never sent for a paid invoice). Failures: temporary (timeout, rate limit, server error) retry 3 times at 1, 5 and 30 minutes; permanent (invalid number, template not approved, parent opted out) do not retry and land on the **"Send these by hand"** list, which is simply the manual queue pre-filled. Sending rate per centre is conservative (about 1 per second, setting). Meta's throughput rules were not read: **not verified**. The worker runs from a daily cron like `api/billing-cron.js` plus a "Send now" button for a staff-approved batch; cron frequency on the current Vercel plan: **not verified**.
6. **Status webhook** `api/wa-webhook.js`: one URL per centre (`?o=<random id>`, because each centre has its own app and so its own app secret and verify token). Verify the GET handshake; on POST read the **raw** body, check `X-Hub-Signature-256` with a constant-time compare (pattern already in `api/stripe-webhook.js`), refuse otherwise; insert `(wamid, status, time)` under a unique key so duplicates are no-ops; statuses only move forward (a late `delivered` after `read` is ignored); store only the message id, status, time and error code, **not** the raw payload. Template status and quality updates update `org_wa_templates` and raise an owner notice. Inbound messages: only to detect opt-out keywords (STOP, UNSUBSCRIBE, configurable); the text is discarded, never stored; no inbox is built (parents' replies reach the centre in WhatsApp Manager / its own number: say so in the UI; whether the same number can also stay in the phone app is **not verified**).
7. **Audit.** `message_log` gets the automatic events too (queued, accepted, delivered, read, failed, with Meta error code), plus audit rows (existing `audit_row` trigger) for: connect, replace, disconnect, settings change, template create, batch approve. **Retention proposal:** log rows (no bodies, no phone numbers, only guardian id) kept 24 months; the rendered parameters in `wa_outbox` nulled 30 days after the message is final; webhook payloads not kept at all. Months to be confirmed with the lawyer (**not verified**).
8. **Cost transparency in the UI.** Each month: messages delivered by kind, an **estimate** = count x the per-message rate the centre types in from Meta's rate card (no rate in our code), the label "Billed to you by WhatsApp, not by TutorDeck", and a link to the centre's own Meta billing. Before a batch: "This will send 312 messages. At your entered rate about S$X. Send?".
9. **Failure never blocks work**: if the connection breaks, a banner appears and the rest of the app (including manual sending) is unaffected.

## 3. Other providers
Worth a **thin adapter**, not a framework: `check(creds)`, `ensureTemplates(creds, kinds)`, `send(creds, template, params, to, idempotencyKey) -> providerMessageId`, `parseWebhook(rawBody, headers, secret) -> events[]`. Implementations: `meta` (direct Cloud API) and `fake` (records calls, can be told to fail, time out, rate-limit, duplicate and reorder events). The adapter costs almost nothing because tests need the fake anyway. **Recommend** not building Twilio or other resellers until a centre actually uses one: their template, id and webhook models differ (**not verified**) and each needs its own review and test account. A `provider` column on the credentials table keeps the door open; other values are `soon`.

## 4. How this fits T4, T7 and the reminder schedule
- **One outbox for all channels.** T7 sketches a `reminders_sent` log; instead build one `message_outbox` + `message_log` with a `channel` column (`whatsapp_manual`, `whatsapp_api`, `email`), so a reminder is never sent twice and the owner sees one history. Flag to the orchestrator: T7 and T4 builders should reuse this table.
- **Invoice delivery (T4):** the WhatsApp message always carries the **share link** (so `invoicing.delivery.share_link` must be on for WhatsApp to be offered); email (`invoicing.delivery.email`, T7/Brevo) is independent and both may be on.
- **Reminders:** the existing `invoicing.reminders.schedule` (e.g. -3, 0, 7) stays the single schedule; new `invoicing.reminders.channels` (multi: `email`, `whatsapp`) says where each reminder goes. A reminder is one outbox row per household per offset per channel.
- **Settings (all `soon` until built, SQL-validated in `org_validate_settings`, enums checked by `tests/org-settings.test.js`, one test per value):**
| Key | Values | Status |
|---|---|---|
| `delivery.whatsapp.mode` | `off` / `manual` (default) / `api` | `api` = `soonOption` until W8; `org_save_settings` also refuses `api` unless a credential is `connected` and the centre has the add-on |
| `delivery.whatsapp.send` | multi: `invoice`, `reminder`, `remark` | `remark` soon |
| `delivery.whatsapp.send_hours` | from / to (Singapore time) | api only |
| `delivery.whatsapp.daily_cap` | number, 1 to the tier | api only |
| `delivery.whatsapp.approval` | `staff_approves_batch` (default) / `auto` | `auto` soon: first release always shows the batch before sending |
| `delivery.whatsapp.fallback` | `manual_list` (built) / `email` | `email` soon |
| `invoicing.reminders.channels` | multi `email`, `whatsapp` | soon, with reminders |
Fixed (integrity and Meta rules, not a choice): no automatic send without recorded opt-in; no send to someone opted out; no message text kept; tutors never trigger parent messages.
- **Wizard wording** (one question, plain): "How do you send invoices and reminders on WhatsApp? **We send them ourselves** (TutorDeck opens WhatsApp with the message ready; you press send. Free, recommended to start.) / **TutorDeck sends them for us** (needs your own WhatsApp Business account; WhatsApp charges you per message it delivers; optional add-on; coming soon) / **We don't use WhatsApp**."
- **Add-on gating:** a feature flag in `org_plans` (`whatsapp_api`) so the add-on can be priced later (decision for the owner; no price is written here).

## 5. Data model, functions, tests, build order
**New tables, all with `org_id`, same-org composite keys, `audit_row`, and no insert/update/delete policy for browsers:** `org_message_templates`, `message_log` (append-only), `message_outbox`, `org_wa_credentials` (no policy at all), `org_wa_templates`, `wa_webhook_events` (dedupe key), plus guardian columns `whatsapp_e164`, `whatsapp_consent`, `consent_at`, `consent_source`, `do_not_contact`. **Functions** (SECURITY DEFINER, pinned search_path, `org_can(...)` checks, `NOT_FOUND` for outsiders and solo orgs): `staff_log_manual_send`, `staff_next_family`, `staff_set_consent`, `wa_credential_status` (state only), `wa_queue_message`, `wa_approve_batch`, `wa_next_due` (server worker only), `wa_record_status`, `wa_record_optout`. Tutors keep zero table access; nothing parent-contact related is added to `tutor_my_lessons`. Credential save/replace/disconnect run through `api/wa-connect.js` with the caller's own token (owner check by RLS, as `api/billing.js`), then the service key only to write the sealed row.

## 7. Risks and decisions for the owner (recommendation first)
1. **When to build.** Recommend: manual W0-W4 right after T4 step S3 (it replaces T4's plain "WhatsApp text" and is the fallback for everything else); automatic W5-W9 **after** the committed first-customer scope. Alternative: do all first (about 22 days) if the first customer's 400-family volume makes hand-sending a blocker.
2. **Credential storage.** Recommend the repo's own sealing method with a server-only key (no plan dependency, precedent in `api/_gcal-lib.js`). Alternative: Supabase Vault once the project's plan is confirmed.
3. **Whose Meta app.** Recommend each centre uses **its own** app and system-user token (matches your decision; no Meta review of TutorDeck needed). Alternative later: TutorDeck as a Meta Tech Provider with a one-click "Embedded Signup" (the docs say partners need App Review approval first; easier for centres, much more work and review for us): keep as `soon`.
4. **Add-on gate.** Recommend a plan flag so `api` can be switched on per centre and priced later; decide price and terms separately with the lawyer.
5. **Approval mode.** Recommend the first release always shows "This will send N messages" and needs a staff click; fully automatic sending stays `soon` until a centre has run clean for a month.
6. **Retention and DNC.** Recommend 24-month log rows without bodies or numbers, and a lawyer check on consent wording and Do Not Call before any real family gets an automatic message. Alternative: keep logs only 6 months.
