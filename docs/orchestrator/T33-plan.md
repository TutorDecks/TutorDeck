# T33 plan: centre data import (wizard step 9 "Import data")

Branch `claude/t33-plan`. Plan only: no product code, no SQL, nothing deployed, LIVE and DEV data untouched. Written 2026-11-26. Customer: "the first managed centre" (about 400 students, about 200 tutors, all 1-to-1). Read: CLAUDE.md, `assets/js/org-settings.js` (step 9 is `custom: "import"`, `importHtml()` says "Coming soon"), `db/migration_org_foundation.sql`, the T3, T4, T6, T7, T24b plans, branches `claude/t3-2-students`, `t3-7-slots` (`staff_save_student`, `staff_save_slot`, `student_tutors`), `t4-s0-settings`, `t4-s1-tables` (`migration_centre_money.sql`), `t7-2-invites` (`api/send-invite.js`), `t24c-2-payout`, and the T27 product guide (step 9 is one line: "Nothing to choose; the owner uploads files"). Anything I did not confirm in code says **not verified**. Sizes are estimates until the fixture runs on DEV.

## Summary
- **One import, owner only, create-only.** The owner downloads 6 CSV templates (a 7th, past lessons, is optional and later), fills them from the centre's sheets, uploads them together. Nothing is written until **every row of every file** passes. The owner then sees a dry-run summary with totals to tick against the sheets, and presses one button for **one all-or-nothing database transaction**. Same file twice = zero new rows.
- **Reuse the screens' own rules.** The commit calls the same database functions staff use (`staff_save_student`, `staff_save_slot`, `org_invite`, `staff_set_student_tutors`), so same-organisation checks, slot clash, audit rows and "students filed under the owner's login" cannot drift. No new way to write a table.
- **No email, ever, during import.** Tutors are created as `memberships.status = 'invited'` with no mail. The owner sends invites later in batches: `api/send-invite.js` on `t7-2-invites` allows **30 per organisation per hour**, so 200 tutors take 7+ hours of sending; plan on 2 days (decision 4).
- **Two stages, so the launch does not wait for money screens.** Stage A (families, students, tutors, weekly lessons) needs only T3 steps 2 and 7 on `dev`. Stage B (deposits, unpaid invoices, tutor pay rates) needs T4 S1/S4/S7 and two small additions (decision 3). Neither T3 nor T4 is on `dev` today (**verified**: `origin/dev` has no `migration_staff_*` or `migration_centre_money` file).
- **Where it runs:** CSV is read in the browser (instant feedback, file never leaves the device); validated rows go to a **staging table**; SQL re-validates everything (the browser is never trusted) and commits. Tables have no browser write policy; functions only.
- **Size is small** (about 2,900 rows in all). Risk is not volume but the **8-second statement limit** Supabase usually puts on API calls (**not verified** for this project): commit budget 5 s, measured on a 400/200 fake fixture; plan B in section 4.
- **Fallback if the build slips:** step I0 (templates + browser validator, no database) ships first. With I0 the owner can already hand the templates to the centre and get clean files; a one-off SQL script generated from validated files, reviewed by the owner, covers the load (section 7).
- **Prerequisite on the calendar:** none of the org, attendance, tutor-access, T3 migrations is on LIVE yet (CLAUDE.md). They need their own SELECT-preview, yes and rollout before an import window that opens 10 December.
- Six decisions for the owner in section 8.

## 1. The templates
**Common rules (all files).** UTF-8 CSV (Excel: "CSV UTF-8"); first row = headers exactly as in the template (any order, case ignored; unknown columns ignored with a warning; columns named like NRIC, birth date, bank or account are a **hard error**: "remove this column, TutorDeck never takes it"). Dates `YYYY-MM-DD` or `DD/MM/YYYY` (day first, never month first). Times `HH:MM` 24 h. Money in dollars, digits and an optional 2-decimal part, no "$" or commas (`55`, `55.50`); the validator turns it into **integer cents** and never uses floats (money.js rule). Yes/No columns: `Y` or `N`. Text is trimmed; a cell starting with `= + - @` is kept as plain text and shown escaped (no spreadsheet or HTML injection). Limits come from the existing functions: names 120, level 40, subject 60, notes 1,000. `*` = required. Every file has a `*_ref` column the centre invents (its own student number, or the sheet's row number); refs are the **matching keys** for re-runs and must never change between runs. All examples below are fake.

## 2. Validate, then commit
**Order of checks** (all in one pass over the whole file set; errors collected, never stop at the first):
1. **File:** readable UTF-8, header row, required columns present, row limits (students 3,000; tutors 1,500; weekly lessons 20,000; deposits and invoices 3,000 each), no forbidden column.
2. **Row:** required, type, length, allowed values (the tables above).
3. **Inside the set:** duplicate keys, a family with two names, two overlapping slots for one student.
4. **Across files and the database:** `family_ref`, `student_ref`, `tutor_email` resolve; email not already the owner or a different role; key already imported (see below).
5. **Rules the screens enforce:** same ones, reused (student not ended, slot clash, pay fields together).

**Report.** A table per file: **line number** (spreadsheet row, header = 1), **column**, **what is wrong**, **how to fix**, e.g. `students.csv, line 17, level: "Pri 5" is not recognised. Use P5.`; `weekly_lessons.csv, line 212, student_ref S0099: no such student. Add S0099 to students.csv or fix the reference.` First 200 per file on screen, **Download all errors (CSV)** for the rest. Three severities: **error** (blocks everything), **warning** (needs a tick, does not block), **note** ("37 rows already in TutorDeck, skipped"). Codes, not values, go to the server (section 5).

**Dry-run summary** (needs zero errors): "**412 students** in 301 families, **198 tutors** (198 invitations saved, **0 emails sent**), **1,640 weekly lessons**, **37 deposits** totalling S$X, **12 unpaid invoices** totalling S$Y. Already in TutorDeck: 0. Warnings: 6." The two money totals are there so the owner can tick them against the centre's own sheets: it is the cheapest check for a mistyped amount. Then a tick box ("the centre may give TutorDeck this personal data", wording from the lawyer, **not verified**) and **Import now**.

**Atomic commit.** One call, one transaction. Inside it, the function re-validates against the database as it is now (someone may have added a student meanwhile), takes a lock so only one batch per centre runs, and writes in the order of section 3. Any error rolls back **everything**; the batch stays "validated" and nothing exists. Validation failures come back as data, not exceptions (so no cell values land in Postgres logs).

**Re-run safety (idempotent, create-only).** Every record has a key: family `family_ref`, student `student_ref`, tutor lowercased email, weekly lesson (`student_ref`, tutor, day, start), deposit (`student_ref`, date, amount, reference), invoice `invoice_number`. A row whose key exists and whose content is the same = **skipped** (note). If its content differs = **skipped with a warning** ("S0001 already exists with a different level; change it in the app; import never overwrites"). The import **never updates or deletes**, so it cannot undo a staff member's edit. A corrected file with 5 new rows adds exactly 5. Child records may be added to existing parents later (stage B on top of stage A). Two identical rows inside one file = error ("add a reference to tell them apart").

**Undo (a "batch").** Every row the commit creates is listed in `import_items(batch_id, table, row_id)`, a side table: no `import_batch_id` column on the hot tables. `import_undo_preview(batch)` lists, per record type, what can and cannot go; `import_undo(batch)` removes the safe ones in one transaction (the sanctioned path; CLAUDE.md says never delete rows by hand, the audit log copies them).

| Imported thing | Undo | Blocked when |
|---|---|---|
| Families, guardians, students, student-tutor links | deleted | the student has a lesson that is marked, invoiced or paid |
| Weekly lessons and the lessons generated from them | deleted | any lesson is marked, charged or on an invoice |
| Tutor invitations | deleted | the tutor has accepted (a login exists): kept, listed |
| Deposits | **reversed** (reversing entry, ledger is append-only) | a refund was requested or paid |
| Opening invoices | **voided** by the undo | a payment is allocated, or the invoice was shared or sent; then the normal fix is a credit note |
| Tutor pay rates | reversed (new row) | a pay run used them |
Undo is offered for 7 days (decision 5), and shows exactly which rows stay and why. Nothing issued to a parent is silently removed.

## 3. Where each record goes
| Record | Table(s) | Called with | Rules that then hold |
|---|---|---|---|
| Family + guardians | `households`, `guardians` | via `staff_save_student` (first student of a family passes the guardians; later siblings pass the household id) | same-org composite key; max 6 guardians; phone or email; the household name is set once |
| Student | `students` (filed under the owner's login), `online_link`, `location`, **new `start_date`** | `staff_save_student` | duplicate name inside a family refused; `contact` / `recipient_name` kept equal to the main guardian |
| Tutor | `memberships` (`role tutor`, `invited`, no user), `phone`, `employment_type` | `org_invite` (owner check, "Already invited", no email) then set phone | tutors have still no table access; `org_claim_invites()` links them when they sign in |
| Student-tutor | `student_tutors` (append-only history) | `staff_set_student_tutors` | `org_tutor_same_org_guard` |
| Weekly lesson | `recurring_slots` with `taught_by`, `rate` | `staff_save_slot` | slot clash; tutor must be in this centre; rate 0-1000; audit row |
| Deposit *(B)* | T4 S4 deposit ledger entry `opening_balance` | the S4 ledger function | per student; no deposit invoice, no number used, no revenue; release rules = a snapshot of today's settings, marked "imported" |
| Unpaid invoice *(B)* | `centre_invoices`, new `kind = 'opening'` | a new `import_*` internal function | issued, immutable, keeps the **old number** as `imported_number`, does not touch the invoice counter; one line from `covers`; payments later allocated by S3 |
| Tutor pay *(B)* | T4 S7 `tutor_pay_rates` (append-only, effective-dated) | the S7 rate function, `effective_from = pay_from` | nothing edited, only new rows |
| Batch bookkeeping | `import_batches`, `import_stage_rows`, `import_items` | `import_*` | `org_id`, composite keys, `on delete cascade`, audit trigger, **no insert/update/delete policy** |

**Not created by import:** lessons (the owner presses "Create lessons for the next 4 weeks", T3 step 7, so no surprise); auth accounts; parent accounts; any email, WhatsApp or reminder. A test checks that no outbound queue or `org_invite_mail_log` row exists after an import, and that no call reaches `api/send-invite`.

**Order of loading:** households and guardians, students, tutors, student-tutors, weekly lessons, then stage B: pay rates, deposits, opening invoices, then mark the batch committed.

## 4. Where it runs, speed, permissions, audit
- **Browser:** small own CSV reader (about 80 lines, quotes, commas, newlines in cells, BOM; no library, no build step), the validator (pure functions in `assets/js/import-core.js`, unit-tested like `tutor-core.js`), the report and summary. Files stay in memory only.
- **Server (database):** `import_begin(org)`, `import_stage_rows(batch, file_type, rows)` in chunks of 500 rows, `import_validate(batch)`, `import_commit(batch)`, `import_discard(batch)`, `import_undo_preview(batch)`, `import_undo(batch)`, `import_history(org)`. `SECURITY DEFINER`, `search_path` fixed, revoked from `public` and `anon`, `NOT_FOUND` for a solo organisation, a non-member or a non-owner (no probing).
- **JS and SQL validators must agree:** one shared file of cases (`tests/fixtures/import-cases.json`: input row, expected code) runs in `tests/import-core.test.js` and in the SQL test, as T4 does for GST. Drift = red test.
- **Size and speed (estimates, not verified):** about 600 guardians, 400 students, 200 tutors, 1,640 slots, 37 + 12 money rows = about 2,900 rows; staging is 6-7 calls of 500 rows; validation is set-based SQL, 1-2 s. The commit loops the existing row functions (about 2,500 calls plus an audit row each). **Budget: commit under 5 s on the DEV fixture.** If it is over, plan B: (1) refactor the row rules into internal set-based helpers that the screens and the import both call (still one rule set); or (2) commit in steps, each its own transaction with a batch status, and if any step fails run `import_undo` on the steps already done (a compensating rollback; allowed only because every row is new and unused). Plan B(2) is the fallback, not the design, because it gives up true atomicity. `staff_generate_lessons` for 1,640 slots over 4 weeks (about 6,500 lessons) has the same limit and needs its own timing; generate week by week if slow.
- **Who:** the **owner** only (`org_can(org,'owner')`). It creates people's invitations, holds personal data of about 600 people, and loads money; `org_invite` is already owner-only. No new permission name (T3/T4 rule). Later option: staff with `manage_students` for the students file only.
- **Concurrency:** one open batch per centre (unique partial index); commit holds an advisory lock; staff can keep working, and a clash is caught at the commit's re-validation.
- **Audit:** `audit_log` rows `import_stage`, `import_validate`, `import_commit`, `import_discard`, `import_undo`: who, when, counts, and the **SHA-256 of each file** (computed in the browser) so the owner can show which file was used, without keeping it. No row contents. The normal per-row audit triggers on the business tables still run (existing behaviour); the money tables redact free text.

## 5. PDPA
- The files hold names, phone numbers and emails of children, parents and tutors. The **centre is the data owner, TutorDeck the processor**; the commit needs the owner's tick (lawyer to word it, **not verified**).
- **Data minimisation by design:** no NRIC, date of birth, school or bank columns; such a column header is refused. Tutors' payout details are never imported.
- **Files are never uploaded as files:** no Storage bucket, no server copy. The browser holds them in memory until the page closes (not in `localStorage`, not through `TL.store`).
- **Staged rows are temporary:** `import_stage_rows` is deleted at commit, at discard, and by a 24-hour expiry enforced on every import call (no cron is assumed; `pg_cron` is **not verified**). After commit only `import_items` (ids) and counts remain, never the cells. A test greps that no `import_*` table holds a column that can contain a name.
- **No data in logs:** import functions return errors as data with codes; `RAISE` messages carry no cell values; the page sends no cell text to `client_errors`. The "Download all errors" CSV does contain values: it is saved on the owner's own device, with a note to delete it.
- **Remote work:** the real file is never put on DEV, in the repo (it is PUBLIC), or in a chat. DEV and tests use only the generated fake fixture. The first dry-run with real data is **validate-only on LIVE** (staged rows, then discard).
- Deleting a centre removes every import table row (`on delete cascade`, covered by the org-delete test); the audit copies made by the row triggers follow the existing org-delete rules.

## 6. UI
- **Wizard step 9** and **Settings > Import** (`/org-import`, a tab of Settings, owner only) are the same component. Desktop only: under 820 px it says "Open this page on a computer."
- **Five steps on one page:** 1 **Templates** (a download button per file, built in the browser, a "how to fill it" table with the fake example row; a note that columns may be reordered). 2 **Upload** (drop up to 7 files at once; each is recognised **by its header row**, not its file name; chips show "students.csv · 412 rows"). 3 **Check** (the report of section 2, filter by file, "Download all errors"). 4 **Confirm** (summary and totals, warnings ticked, consent tick, **Import now**; one primary button per screen). 5 **Done** (counts; next actions as links: "Send invitations", "Create lessons for the next 4 weeks", "Undo this import").

- Look and feel as the rest of the app (Manrope, teal as the only accent, errors in owed red, warnings in amber); `TL.coach` one-time tip on step 1.

## 8. Risks and decisions for the owner (recommendation first)
1. **Owner-only, create-only import.** Recommend: only the owner imports; the import adds and never updates or deletes; a mismatch is fixed in the app. Alternative: allow updates by key (powerful for sheets kept alive elsewhere, but a stale sheet could overwrite staff corrections).
2. **Stage A first, money later.** Recommend: launch the first centre on stage A (families, students, tutors, weekly lessons) as soon as T3 steps 2 and 7 are on `dev`, and load deposits, unpaid invoices and pay rates in stage B as T4 S1/S4/S7 land. Alternative: hold the whole import until T4 S7 exists; the centre then starts later than 10 December or runs partly on its sheets.
3. **Two small data-model additions.** Recommend: (a) a new invoice `kind = 'opening'` in T4 S1 that keeps the **old invoice number** and does not use the counter (S1 today allows `lesson`, `deposit`, `late_fee`, `credit_note` and requires a counter number on every issued invoice: **verified** in `migration_centre_money.sql`); (b) a nullable `students.start_date`, which T4's "first month's fee" needs anyway.
