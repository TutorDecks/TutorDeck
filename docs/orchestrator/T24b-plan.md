# T24b plan: Settings for tutors who work under a centre

Branch `claude/t24b-plan`. Plan only: no product code, no SQL. Written 2026-11-25 from CLAUDE.md, `api/delete-account.js`, `db/migration_org_foundation.sql` / `_tutor_access.sql` / `_org_delete.sql`, `assets/js/password-rules.js`, `assets/js/tutor.js`, and the T3 / T7 plans and branch `claude/t24-settings-closed` (v266).

## Summary
- **New small page `/tutor-settings`** (file `tutor-settings.html` + `assets/js/tutor-settings.js`), reached from a link on My lessons (and More, for "both" logins). The solo `/settings` page **stays closed** to tutor-only logins (v266 redirect untouched).
- **Three blocks:** Profile (name, phone, email read-only, change password, sign out), **Payout details** (PayNow mobile / PayNow UEN / bank account), **Delete my account**.
- **Same rule as My lessons: tutors have no table access.** Every read and write goes through new SECURITY DEFINER functions with explicit column lists: `tutor_my_profile()`, `tutor_save_profile(...)`, `tutor_my_payout()`, `tutor_save_payout(...)`, `tutor_clear_payout()`.
- **Payout details live in a new append-only table** `tutor_payout_details` (org_id + membership_id). The tutor never touches it; the centre reads it only through `org_tutor_payouts(org)`, which needs a **new permission `view_payout_details`** (owner always; staff only if granted). Full numbers are shown only on an explicit "Reveal", and every reveal is audited.
- **Delete account = "Remove me from this centre" request, not an instant delete (recommended).** The tutor asks; the centre owner approves in one tap; then the server erases the login and personal data but **keeps lessons and attendance, shown as "Former tutor"**. A "both" tutor keeps their solo account and just leaves the centre.
- **Encryption:** plain columns behind SECURITY DEFINER + RLS now (the data is a payout destination, like the PayNow number printed on every invoice); field-level encryption for the **bank account number only**, as a later hardening step (decision 4).
- **PDPA:** collect only what is needed to pay; show last 4 by default; log who revealed it; erase on removal; delete payout history 12 months after the person leaves (or earlier on request).
- **7 small steps** (section 6), DEV only, each with tests. Nothing goes to LIVE until the owner ships.
- Out of scope: tutor pay itself (T4), centre-side screens (T3/T4; only the permission and the list function are here), parent-facing anything.

Needs the **current password** first (re-sign-in with `signInWithPassword`, then `updateUser`). Both-mode logins change the one password for both roles; the page says so. |

Plain-words copy, one teal primary button per block ("Save"), nothing else teal.

## 2. Payout details
**What a tutor enters** (one method at a time; they can change method later):
| Method | Fields | Validation (JS and SQL both) |
|---|---|---|
| **PayNow mobile** | mobile number | `+65` then 8 digits starting 8 or 9 (`^\+65[89]\d{7}$`, spaces/dashes stripped on entry) |
| **PayNow UEN** | UEN | 9 chars `^\d{8}[A-Z]$` (business), 10 chars `^(19|20)\d{2}\d{5}[A-Z]$` (local company), or `^[TSR]\d{2}[A-Z]{2}\d{4}[A-Z]$` (other entity); stored upper-case. Checksum is not enforced (UEN checksum rules differ by type); a wrong UEN is caught by the centre's first PayNow test payment. |
| **Bank account** | bank name (pick-list of SG banks + "Other"), account number, account holder name | number: digits only after stripping spaces/dashes, 7-16 digits; holder name 2-80 chars; the page says "Name must match your bank account". |

Always also: `updated_at`, and a tick "I confirm these are my own details."

**Where stored.** New table `tutor_payout_details`: `id`, `org_id`, `membership_id` (FK, same-org composite key like `lessons_taught_by_same_org`), `method` (`paynow_mobile` / `paynow_uen` / `bank`), `paynow_id text`, `bank_name`, `account_no`, `account_holder`, `created_at`, `created_by` (always the tutor's login), `superseded_at` (null = current). **Append-only like `org_settings`:** a change inserts a new row and sets `superseded_at` on the old one (done inside the function, never by a client); the existing `audit_immutable()` trigger blocks update/delete except the `superseded_at` column and the removal erase (below). One current row per membership (partial unique index). RLS on, **no policy for any browser role**; only the functions read it. This is how CLAUDE.md wants it: tutors have no table access.

**Who can read.**
- Tutor: only their own current row, via `tutor_my_payout()` (masked by default: PayNow `+65 ••••• 1234`, bank `•••• 5678`; "Show" fetches full value from `tutor_my_payout(reveal => true)`, tutor only sees their own).
- Centre: `org_tutor_payouts(org)` returns masked rows for the list; `org_tutor_payout_reveal(org, membership)` returns one full row and writes an audit row "revealed". Both need **`view_payout_details`** (owner always has it; staff only if granted in People). **Recommendation: a new permission, not `issue_invoices`.** Reason: `issue_invoices` is about money coming in from parents; bank details of staff are personal data and a front-desk person who prints invoices shouldn't see colleagues' bank accounts. It costs one line in the catalogue (`org-settings.js`), `org_invite()`/`org_set_permissions` allow-list and the permission tests; the existing 8 names stay valid.
- Parents, other tutors, platform admins: never. (Support access grants do not cover this table.)

**Audit log.** Triggers write `payout_saved` / `payout_cleared` / `payout_revealed` rows with who, when, membership and method; **the audit `before`/`after` JSON stores only the masked value (last 4) and method, never the full number** (the generic `audit_row()` would copy whole rows, so this table gets its own trigger and the generic one is not attached). Tutors cannot read the audit log; the owner (`view_audit_log`) sees "Tutor One changed payout method to PayNow mobile, 25 Nov 14:02".

**History.** Superseded rows stay (append-only) so the centre can answer "which number did we pay on 3 Nov?" (T4). The owner screen shows current only; history is a "Show history" link behind `view_payout_details` with masked values.

**Heads-up to the centre.** Changing payout details is a classic fraud route ("please pay a new account"). So: change writes the audit row, the centre sees "Changed on 25 Nov" with an amber tag for 7 days in the tutors list, and a centre setting `payouts.change_notice` (`owner_only` default / `none`; `soon` until T4 builds the email) decides who is told. The tutor sees the same warning "Your centre will see this change".

**PDPA (Singapore).**
- *Purpose and consent:* the page says in plain words why it is collected ("so your centre can pay you") and who sees it; the save needs the tick above. TutorDeck is the **data intermediary** and the centre is the **organisation responsible**; this goes in the centre terms (owner to confirm with the company's adviser; not legal advice).
- *Minimisation:* no NRIC, no bank statements, no address, no date of birth. Optional phone only.
- *Access/correction:* a tutor sees and edits their own details at any time (this page); "Download my data" for tutors is a later add-on.
- *Retention:* current row kept while the membership is active; on removal the **current row is erased at once** (it has no further purpose); superseded rows are erased **12 months after removal** (money-record look-back, owner may shorten; decision 5). Audit rows hold only masked values, so they can stay.
- *Security:* only the functions, masked by default, reveal is logged, HTTPS only, no value ever in logs, URLs or error text (`api/*` rule already says never log row contents).
- *Breach plan:* the existing incident process; listed so the owner knows the notification duty (PDPC within 3 days if significant harm) applies if bank numbers leak.

**Encrypt at rest? Recommendation: not now for PayNow; yes later for bank account number.** Supabase already encrypts the disk and backups at rest; the weak spot is *who can query*, which RLS-with-no-policy plus functions covers. pgsodium/Vault column encryption adds key handling, makes the nightly encrypted backup and restore tests harder, and is only worth it if a service-role leak is the threat (then the key in the same project falls too, unless held in Vercel env). Plan: ship plain behind functions (step 3); add the optional step 8 "encrypt `account_no` with a key held in a Vercel server env var, decrypt only inside `api/payout.js` when revealing" only if the owner wants it. This is decision 4.

## 3. Delete account for a centre tutor
**What is correct.** A centre's lessons, attendance and (later) pay records are the **centre's** records and must outlive the tutor. The person's **login and personal data** are theirs to take back. So:
- Erased: auth login, `profiles` row, `memberships.display_name` / `invited_email` / `phone` (replaced by `Former tutor`, nulls), `memberships.user_id` (null), payout rows (current at once), the tutor's Google/gcal link if any.
- Kept: the `memberships` row itself (new status **`removed`**, `removed_at`), every lesson with `taught_by` still pointing at it (shows as "Former tutor"), attendance marks, remarks, audit rows (the actor column is the old user id; after removal it matches nothing, which is the intent).
- **Why not just delete the membership row?** `lessons.taught_by` is `on delete set null`, so the lesson would lose who taught it and show a blank tutor; and `memberships.user_id` is `on delete cascade` from the login, so deleting the login would delete the row. Both are fixed by nulling `user_id` first.

**DB changes needed** (migration `migration_tutor_remove.sql`, DEV first):
1. `memberships.status` check gains `'removed'`; `memberships.removed_at`, `removed_by` (null = self); relax `check (user_id is not null or invited_email is not null)` to also allow `status = 'removed'`; guard `lessons_taught_by_guard` and `org_can*` already ignore non-`active`; add `removed` to the unique-email-per-org rule so the same address can be re-invited later as a new row.
2. `org_remove_tutor(p_org, p_membership, p_by uuid, p_reason)` (service_role only, SECURITY DEFINER): checks the role is `tutor` (never owner/staff: owner transfer first), sets the transaction flag `td.removing_member` = that membership id (the only exception to the append-only/audit rules, same pattern as `td.deleting_org`), erases payout rows and personal columns, sets status, writes **one** `tutor_removed` audit row (membership id + role, **no name/email**), and returns counts. Never touches the lessons table (a test proves lesson row counts and `taught_by` are unchanged).
3. Because `audit_row()` would copy the old name/email into the audit log when `memberships` is updated, the function sets `td.skip_audit` for that one update (transaction-local, like `org_delete_solo`). **Existing audit rows that already hold the person's name/email** (from invites and edits) are scrubbed by the same function for that membership id (`before`/`after` fields `display_name`, `invited_email`, `phone` replaced by `"[removed]"`), allowed only under the flag. The audit table's append-only guard gets this one extra exception, with a test that nothing else is updatable.
4. `org_before_user_delete` safety net: if a login is deleted while it has centre memberships, run `org_remove_tutor` for each `tutor` membership first (so nobody can end up with orphaned personal data), and **refuse** (`IS_CENTRE_OWNER`) if they own or staff a centre.

**`api/delete-account.js` changes.** Today it answers `409 has_other_orgs` for any centre member. New behaviour (one server function, two modes):
| Caller | Result |
|---|---|
| Solo only (today) | unchanged |
| Centre **tutor only** | `confirm: "DELETE"` + the request has been **approved** (see below), then: step 1 find all memberships; step 2 `org_remove_tutor` for each tutor membership; step 3 Google token revoke; step 4 delete login. No Stripe/storage (tutors have none; check anyway). |
| **Both** (solo + centre tutor) | page offers two separate buttons: **"Leave this centre"** (calls `org_remove_tutor`, login and solo data untouched, solo tutor keeps the account) and the existing solo "Delete my account", which first removes the centre tutor memberships, then runs the solo steps. The 409 stays only for owner/staff of a centre ("transfer ownership or ask the owner to remove you first"). |
| Centre owner/staff | still refused with plain words (out of scope; owner transfer is its own task). |

**Centre owner/staff removing a tutor** is different: it is the centre's decision, needs `manage_tutors`, calls `org_remove_tutor_by_admin` (a normal authenticated function that checks `org_can(org,'manage_tutors')` and then does the same erase of **centre-held** data only: sets the membership `removed`, erases payout rows and phone, keeps the **login alive** (the person may teach elsewhere or have a solo account). The tutor's login is deleted only by the tutor themselves (or when it was an invite-only account that never signed in and has no other memberships: then delete that stub login too). The tutor is told "X removed you" by their next sign-in message; email is `soon` (needs T7).

**Audit rules (summary).** The audit log stays append-only. Exceptions are exactly: `td.deleting_org` (solo, existing), `td.removing_member` (this plan). Both are transaction-local, set only inside the function, never by a client, with tests that a direct client `update/delete` on `audit_log` still fails. One audit row survives each removal: **action, role, membership id, who (null for self), when**; no personal data.

**What the tutor must confirm.** Screen text: "You are about to remove yourself from **{centre}**. Your login, name, phone and payout details will be erased. Lessons you taught stay in the centre's records and will show as *Former tutor*. This cannot be undone." Then type the word `DELETE` (existing pattern), re-enter the password, and tick "I have been paid for all lessons / I know my centre may still owe me" (so a tutor doesn't erase payout details before payment; the centre keeps its own pay record, T4). If the tutor also has a solo account, the screen says which of the two buttons does what.

**Self-service or ask the centre first? Recommendation: ask first (request, owner approves), with a 7-day auto-approve.** Reasons: (a) the centre may owe pay or hold open lessons; (b) CLAUDE.md principle: anything depending on the centre's process is the centre's setting. So `members.tutor_self_leave` = `owner_approves` (default) / `immediate` (centre chooses; both built and tested). In `owner_approves` the tutor presses **"Ask to leave"**: a row in `tutor_leave_requests` (org_id, membership_id, requested_at, status), the owner sees it in People, one tap to approve (then the erase runs and the tutor's login deletes on the tutor's **next confirmation**: the final step needs the tutor's own token, so the page shows "Approved: press Finish" or the API runs on the next sign-in); after 7 days with no answer the tutor may finish by themselves (so a missing owner can't trap anyone: a PDPA withdrawal-of-consent and deletion request must be honoured promptly). The tutor can also email privacy@ at any time; the owner's runbook covers it.

## 6. Build steps (each its own branch off `dev`, DEV only; `?v=` bump + README log each)
1. **Page shell + Profile (name, phone, read-only email, sign out).** Migration part A (`memberships.phone`, `tutor_my_profile`, `tutor_save_profile`). *Done =* tutor.one opens `/tutor-settings` from My lessons, edits name/phone, they persist, tutor.two unaffected; `/settings` still redirects for tutor-only. *Click-through:* sign in as tutor.one → My lessons → Settings → change phone to `+65 9123 4567` → save → reload → it shows.
2. **Change password.** Uses `PasswordRules`; current-password re-check; waits for T7's shared reset-page fix or does the same inline. *Done =* weak password shows the "Still needed" list; good one works; sign in with the new one. *Click-through:* as `both.tutor` change password, sign out, sign in with the new one (then change back).
3. **Payout details (tutor side).** Migration part B (table, functions, validators, masking, audit). *Done =* all three methods save, mask, reveal; bad input is refused with plain words. *Click-through:* tutor.one saves PayNow mobile `+65 8123 4567`, sees `•••••4567`, taps Show; tutor.two sees nothing of it.
4. **Permission + centre list.** `view_payout_details`, `org_tutor_payouts`, reveal. *Done =* centre.owner sees masked list and can reveal (audited); a staff login without the permission sees "provided". *Click-through:* centre.owner → People → tutors list → reveal tutor.one's PayNow → open the audit log and see the reveal.
5. **Leave-centre / delete (DB first).** Migration part C (`removed` status, `org_remove_tutor`, audit exceptions, safety net). SQL tests only; no UI. *Done =* `tests/sql` green incl. "lessons unchanged".
6. **Delete UI + `api/delete-account.js` + request flow.** *Done =* tutor.two asks to leave; centre.owner approves; tutor.two's login is gone, tutor.two's past lessons show "Former tutor"; both.tutor "Leave this centre" keeps their solo students. *Click-through:* as above, then sign in as centre.owner and open a past lesson of tutor.two.
7. **Centre removal + owner Settings section.** `manage_tutors` "Remove from centre", the two settings in the wizard. *Done =* owner removes tutor.one; tutor.one can still sign in (no centre) and sees "You were removed from Demo Centre"; payout rows gone.
8. **(Optional) bank-number encryption** (decision 4) and "Download my data" for tutors.

## 7. Risks and decisions for the owner (recommendation first)
1. **Delete = request the centre first, auto-OK after 7 days?** Recommend **yes**; alternative: instant self-delete (fast, but a tutor can erase payout details while still owed pay, and the centre has no say, which breaks "the centre decides").
2. **Permission for payout details:** recommend a **new `view_payout_details`** (owner always, staff opt-in). Alternative: reuse `issue_invoices` (no new name, but a receptionist who prints invoices could see bank accounts).
3. **What stays after someone leaves:** recommend **lessons and attendance stay as "Former tutor"; name, phone, email, login and current payout erased at once; old payout rows erased after 12 months.** Alternative: erase everything incl. tutor name on lessons (loses who taught what for disputes and T4 pay history).
4. **Encryption:** recommend **plain now (functions, masked, audited), bank account encryption later** with a server-held key. Alternative: pgsodium/Vault from day one (more moving parts; backup restore tests get harder).
5. **Retention period** for old payout rows: recommend **12 months** after removal (owner can shorten); needs the owner to confirm with the company's adviser; not legal advice.
6. **Who is told when payout details change?** Recommend the **centre owner sees it in the list (amber for 7 days)**, email later with T7; alternative: no flag (cheaper, but weaker against "please pay a new account" fraud).

Other risks, handled in the build: (a) the generic audit trigger would copy full numbers or names, so payout and membership removal use their own audit writes (tests check); (b) bank numbers must never appear in logs, URLs or error text; (c) a "both" tutor changing password changes it for both roles (page says so); (d) `status='removed'` must be excluded wherever `active` memberships are counted (centre fee job counts billable students, not tutors, so unaffected; checked in step 5 tests); (e) a tutor with no centre left must not be stranded: `TL.detectRole()` already falls back to "solo", and Home then shows the normal empty solo state, which step 7 verifies.
